## 2. Frontend API Client Configuration

### Base URL Mismatch (CRITICAL)

**File:** `frontend/src/api/client.js:3` and `frontend/src/api/admin.js:3`

Both default to `http://localhost:8000` but the FastAPI server runs on port **7860** (`server.py:452`). Without setting `VITE_API_BASE_URL`, all frontend API calls will fail in development.

**Fix:** Change default to `http://localhost:7860` in both files, or document `VITE_API_BASE_URL=http://localhost:7860` as required.

### Admin API Auth Header (CRITICAL)

**File:** `frontend/src/api/admin.js:9-14`

Admin API client sends `Authorization: Bearer ${apiKey}` header, but the backend admin routes expect `X-Admin-Key` header (`api/auth.py:19`). Furthermore, `get_client_from_token` explicitly **rejects** admin keys sent as Bearer tokens (`api/auth.py:46-47`). The admin frontend is DOA with this config.

**Fix:** Admin interceptor should set `config.headers['X-Admin-Key'] = apiKey` instead of `Authorization: Bearer`.

## 3. Endpoint Mismatches

### 3.1 `POST /api/campaigns` — Does NOT exist (HIGH)

**Frontend:** `Dashboard.jsx:323` — `clientApi.post('/api/campaigns', newCampaign)`

**Backend:** No `POST` route exists on the client `/api/campaigns` router. Campaign creation is only available via `POST /internal/campaigns` (admin-only). The frontend catches the error and falls back to local simulation, but this is a dead code path that will always 404.

**Status:** The wizard modal is currently commented out in the UI (`Dashboard.jsx:651-825`), so users cannot trigger this. Safe for now, but the code should be cleaned up or the TODO made explicit.

### 3.2 `PATCH /api/campaigns/{id}` (settings save) — Does NOT exist (MEDIUM)

**Frontend:** `CampaignDetail.jsx:393` — `clientApi.patch('/api/campaigns/${id}', { name, max_concurrent_calls, ... })`

**Backend:** No `PATCH /api/campaigns/{id}` route exists on the client API. The settings edit route exists only at `PATCH /internal/campaigns/{id}` (admin-only). The Settings tab is commented out (`CampaignDetail.jsx:956-1020`), so this code path is unreachable. But `handleSaveSettings` function remains as dead code.

### 3.3 `call_logs` missing `name`, `phone`, `status` columns (HIGH)

**Frontend:** `CallLogs.jsx:319-321` displays `call.name`, `call.phone`, `call.status` from `/api/calls` response.

**Backend:** `list_call_logs` does `SELECT * FROM call_logs` — the `call_logs` table has NO `name`, `phone`, or `status` columns. These exist on the `leads` table. When real data loads, these fields will all be `undefined`. The `status` field in the mock fallback uses values like `'completed'`, `'follow_up'`, `'voicemail'`, `'failed'` — but the actual backend uses `outcome` (values: `Interested`, `Not_Interested`, `Busy`, `Callback_Requested`, `Wrong_Requirement`, `Unknown`).

**Fix needed:** Either JOIN leads on the backend query to include lead name/phone, or the frontend should use `call.outcome` and display the lead's name via a separate lookup. The `duration_seconds` column IS on `call_logs` and will work correctly.

### 3.4 `call_logs` transcript key name (MEDIUM)

**Frontend:** `CallLogs.jsx:429` and `CallTranscriptDrawer.jsx:164` read `callData.transcript`

**Backend:** The `call_logs` Postgres column is named `transcript` (JSONB). This matches! ✅ However, the mock data uses a simplified structure `{ role, content }` while backend stores `{ role, content, ts }`. The frontend handles this correctly since it only reads `role` and `content`.

### 3.5 CallLogs `time_label` field — Does NOT exist on backend (LOW)

**Frontend:** `CallLogs.jsx:328` — `call.time_label || formatDateTime(call.created_at)`

**Backend:** `call_logs` has no `time_label` column. The fallback to `formatDateTime(call.created_at)` will work with real data since `created_at` exists. This is fine, but the mock data with `time_label: '10:42 AM'` can be misleading.

## 4. Mock / Placeholder Data

### 4.1 Dashboard — 6 Hardcoded Prototype Campaigns (HIGH)

**File:** `Dashboard.jsx:67-147` (and duplicated at lines 162-242)

Six fake campaigns are always injected into the campaign list, even when the API returns real data. They use fake UUIDs like `'campaign-1-uuid'` through `'campaign-6-uuid'`. The code merges them by checking `mc.id === dc.id`, so they only appear if no real campaign has the same ID. But since real UUIDs are different, **all 6 mock campaigns will always appear alongside real ones**.

One mock campaign uses `status: 'failed'` — which is NOT a valid campaign status in the backend schema (valid: `draft`, `running`, `paused`, `completed`, `cancelled`).

The mock data is duplicated across two code blocks (success and error paths) — DRY violation.

**Fix:** Remove the `defaultCampaigns` injection entirely. Show an empty state with a CTA when no campaigns exist.

### 4.2 Dashboard — Hardcoded Quick Stats (HIGH)

**File:** `Dashboard.jsx:497-522`

Three stat cards display entirely hardcoded values:
- "Total Minutes: **142,840**" with "+12%"
- "Active Bots: **24**" with "+8%"
- "Concurrency: **480/500**" with "Steady"

None of these come from any API call. The backend has `GET /api/credits` (returns `max_concurrent_calls`) and the campaign list has real counters. No "total minutes" or "active bots" endpoint exists.

### 4.3 Dashboard — Mock Credit Balance Fallback (MEDIUM)

**File:** `Dashboard.jsx:44`

### 4.4 CampaignDetail — Mock Campaign Fallback (MEDIUM)

If the API fails AND no localStorage cache exists, a full mock campaign named "Q4 Real Estate Outreach" with fabricated stats is shown. This creates confusion between real and simulated data.

Bot Strategy card in Overview tab shows hardcoded "Sales Specialist Bot" and "5 credits/minute" regardless of actual bot_config. The backend returns `bot_config_id` on the campaign but not bot details — would need a separate endpoint or JOIN.

## 6. Missing Error Handling

### 6.1 Silently Swallowed API Errors

Every API call in the frontend follows a pattern of `catch(err) → console.warn → fall back to mock data`. This means:

- **401 Unauthorized** (expired/invalid token) — shows mock data instead of redirecting to login
- **503 Database unavailable** — shows fake campaigns
- **Network errors** — shows fake data

Users have no way to distinguish between "API works with real data" and "API is down and showing fake data".

### 6.2 No Token Expiry / Refresh Logic

`Login.jsx` stores the API key in `localStorage` forever. There's no:
- Token validation on page load
- Auto-redirect to login on 401 responses
- Session timeout logic

`ClientGuard` (`Guards.jsx`) likely just checks for key presence in localStorage, not validity.

### 6.3 No Loading States for Campaign Actions

`handleToggleCampaign` (Dashboard), `handleToggleState` (CampaignDetail) — no loading indicators while the API call is in flight. User can click multiple times.

### 6.4 Upload Error for Non-CSV/XLSX

`CampaignDetail.jsx:334-338` — only checks file extension, not actual file content or backend error response.

## 8. UI Improvements

### 8.1 Campaign Cards — Show Real Stats

Replace hardcoded "+12%", "+8%", "480/500" stat cards with real data from `/api/credits` and aggregated campaign stats. Possible computed values:
- Total active calls: Sum `calling_leads` across running campaigns
- Credits remaining: From `/api/credits` response
- Active campaigns: Count campaigns with status `running`

### 8.2 Call Logs — Lead Name Resolution

The call logs table shows `call.name` which doesn't exist on `call_logs`. Options:
1. Backend JOIN: `SELECT cl.*, l.name, l.phone FROM call_logs cl LEFT JOIN leads l ON cl.lead_id = l.id`
2. Frontend: Fetch lead details for each call (expensive)
3. Denormalize: Add `lead_name` and `lead_phone` to `call_logs` at insert time

Option 1 is recommended.

### 8.3 Call Logs — Use `outcome` Instead of `status`

Frontend maps `status` → display labels (`'completed'` → "Completed", `'follow_up'` → "Follow-up Required"). Backend uses `outcome` with different values. Frontend should map `outcome` values:
- `Interested` → green "Interested" badge
- `Not_Interested` → grey "Not Interested"
- `Busy` → amber "Busy"
- `Callback_Requested` → amber "Callback"
- `Unknown` → grey "Unknown"

### 8.4 Campaign Detail — Use Real Bot Config Info

Instead of hardcoded "Sales Specialist Bot" / "5 credits/minute", fetch bot config details. Would require either:
- Backend returning bot config info in campaign stats response, or
- A new `GET /api/bot-configs/{id}` client-facing endpoint

### 8.5 Empty States

When no campaigns exist or no calls logged, the UI should show helpful empty states instead of falling back to mock data. E.g., "No campaigns yet — contact your Aakashvani account manager to set up your first campaign."

### 8.6 Real-Time Calling Count

Replace the random ticking counter (`CampaignDetail.jsx:176-188`) with actual polling of `/api/campaigns/{id}/stats` every 5-10 seconds for running campaigns. The `calling_leads` denorm counter on campaigns is already maintained in real-time by the backend.

### 8.7 Footer Copyright Year

`Login.jsx:181` — "© 2024 Aakashvani" should be "© 2026 Aakashvani".

## 10. Auth & Security Issues

### 10.1 Login Bypass (CRITICAL)

`Login.jsx:52-55`: Keys equal to `'SECRET'` or with `length > 24` skip API validation entirely.
`Login.jsx:71-74`: On API error, keys with `length > 12` succeed ("demo/simulation mode").

**These must be removed before any production deployment.**

### 10.2 Admin API Auth Mismatch

`admin.js` sends `Authorization: Bearer` but backend expects `X-Admin-Key`. All admin routes will fail.

### 10.3 No CSRF Protection

Credentials stored in localStorage, not httpOnly cookies. While this is standard for SPAs with API keys, the comment "Enterprise-Grade Security" in `Login.jsx:181` is misleading.
